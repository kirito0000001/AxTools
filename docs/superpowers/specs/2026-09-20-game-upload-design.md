### 限速说明（现状含义）

```nginx
limit_rate_after 64m;   # 每个连接：前 64 MB 不限速
limit_rate 8m;          # 之后每个连接限 8 MB/s
limit_conn perip 6;     # 同一个 IP 最多 6 个并发连接
```

- 单连接下 916.7 MB 的容器 ≈ 前 64 MB 全速 + 852 MB ÷ 8 MB/s ≈ **1 分 47 秒**。
- 启动器开多连接（最多 6）时是**每连接各自 8 MB/s**，所以并行下载反而更快（上限受 VPS 自身带宽约束）。
- 小文件（清单、小 pak）基本都在 64 MB 那条"不限速"里，**不受影响**。
- 结论：**先不调**。真要调，改两个数字 + `nginx -s reload` 即可，随时可做。

## chunk 与 UE patch pak 的准确关系（2026-09-20 修正）

之前一句话概括成"chunk 管归属、patch 管变更，是两件事"，**不准确**。准确的说法是：

- 两者**达到的是同一个效果**：只让玩家下变化的那部分。
- 差别在**粒度下限**和**代价**：

| 方案 | 只下变更？ | 重下量 | 代价 |
| --- | --- | --- | --- |
| chunk（现状） | 是（未变容器字节相同，已实测） | = **变化所在的整个容器**（最大 chunk0 = 916.7 MB） | 把容器切细；容器数变多 |
| UE patch pak（`_P`，基于基线） | 是 | 只含本次变更的资产（几 MB 量级，待验证） | 多一套打包模式 + 客户端挂载验证 + 契约多一类条目 |

所以"分好 chunk 就等于 patch"这句**在效果上对、在粒度下限上不对**：
chunk 的最坏重下量由容器大小决定，patch 与容器大小无关。

## chunk 实际上已经承担了 patch 的职责（2026-09-20 认定）

用户原话：「我之前已经和你一起研究过**检测新的资源进新的 chunk**了。虽然有点无语，但是确实是
走了一个路子把 patch 替代了，所以 **chunk 已经把 patch 的工作基本都做了**。」

这条结论成立，而且它有具体的机制对应关系：

| patch 想解决的事 | 现有 chunk 机制怎么接的 |
| --- | --- |
| 本次新增的内容单独成一个小包 | 二游打包的《常规补丁更新》= **新资源单独成包**：新资源被分到新的 chunk 号，于是天然是一个新容器 |
| 玩家只下变化的那部分 | 未变的容器字节完全一致（见「实测判决」），文件级清单直接跳过 |
| 不动老内容就不重下老内容 | 老 chunk 不变 → 不下 |

换句话说：**「新资源 → 新 chunk → 新容器」这条链，把 patch 最常遇到的场景（本次新增）直接覆盖掉了**，
而且不需要额外的补丁机制、不需要基线、也不需要客户端挂载改造。

唯一还要留意的边界（也就是「粒度下限」那条的意思）：**如果改动落在已有的老容器里**
（比如改基础包里一张老图，基础包是一个 916.7 MB 的容器），玩家仍然要下整个容器。
这正是"把大容器切细"要解决的问题 —— 见下节，切细由用户自己按目录分。

> **chunk 的分配不再由插件侧改动**（用户 2026-09-20 确认：「chunk 已经不用再改了，我自己之后分一下就行」）。
> 也就是说：
> - 插件/脚本侧保持现在的「目录 → chunk 号」规则结构不变；
> - 大容器怎么拆细（含是否试 `MaxChunkSize`），由用户自己在二游打包页分；
> - 本设计只在**分发侧**（清单、传输、落点）做改造。
