# 幻杀接入 · 零境整链路研读与通用化方案

> 状态：2026-10-19 只读研读，未改代码。
> 目标：先对齐“零境这一整条流程”的真实实现，再判断幻杀“同等待遇”要改哪些层，避免一上来就抽象错。
> 结论先行：**服务端更新和游戏包上传在 AxTools 里已经有幻杀的通用入口；真正缺的是碎片链路，以及幻杀启动器还在用旧版清单格式。** 碎片不是简单复制三份，最好先抽 `GameProfile`。

---

## 0. 结论摘要

零境现在有三条独立链路：

| 链路 | 做什么 | AxTools 入口 | 目标服务器 |
|---|---|---|---|
| 游戏包上传 | 把客户端打包产物按文件推到下载站，生成 v1 清单和 `latest.json` | 服务器 → 零境交错 → 客户端发布（下载站） | `yecaoyun-hk` / `dl.crossingvoid.top` |
| 服务端更新 | 把游戏服务端构建导进 Git 仓库，推送后切换线上目录并重启 | 服务器 → 零境交错 → 服务端更新 | `crossing-server`（阿里云 Windows） |
| 碎片生成/发布 | 把客户端产物切成网盘包；安卓从 OBB 拆条目；只把 `fragments.json` 传下载站 | TFAC启动平台 / 平台-零境-安卓 → 碎片制作页签 | 本地 + `yecaoyun-hk`（只放清单） |

幻杀当前状态：

- **服务端更新**：`ServerProgramCatalog` 已有 `fantasyproject`，远端 `watchdog.config.psd1` 也有 `FantasyProject` 实例；这条链路基本是现成的。
- **游戏包上传**：`FantasyGameAdapter`、`Invoke-FantasyGameAction.ps1`、`FantasyGamePage` 都已接上，产品段 `fantasyproject`、版本标记 `FantasyProject.version.json`；但**幻杀安卓启动器读的是旧 schema v2 清单**，不是 AxTools 内核写的 v1，二者目前没有对接。
- **碎片**：完全没有幻杀入口；所有 `CrossingVoid*` 服务、页面判断、包名前缀、标记名、OBB 旁车、输出目录都写死了零境。
- **产物规模**：幻杀 PC 约 374 MiB、32 个文件，1 片就够；安卓 APK 约 67 MB、OBB 约 49 MB/10 条，安装包 + 1 个基础碎片，共 2 个 zip。比零境轻很多，适合先把通用化跑通。

## 1. 零境整链路

### 1.1 两台服务器，别混

- `crossing-server`：阿里云 Windows，跑游戏服务端进程；服务端更新走这里。
- `yecaoyun-hk`：Linux 下载站，`/srv/downloads`；游戏包/碎片清单走这里，公网 `dl.crossingvoid.top`。

零境的“服务器更新”和“上传游戏到服务器”不是同一台机器、也不是同一套脚本。幻杀同样要分成这两条。

### 1.2 游戏包上传（下载站）

入口：服务器页 → 游戏页签（零境交错 / 火影BP / 幻杀）→ 客户端发布卡片。

代码链路：

```
MainWindow.xaml.cs
  → ServerAliyunPage.AttachGamePublishPanel("crossingvoid", CrossingVoidGamePage)
  → GameUploadAdapter（CrossingVoidGameAdapter / FantasyGameAdapter）
  → Scripts/Adapters/<游戏>/Invoke-<游戏>Action.ps1
  → Scripts/Adapters/GameUpload/Invoke-GameUploadAction.ps1
  → Scripts/Publishing/Games/Publish-GameDownloadRelease.ps1
```

适配器只提供产品段名；版本标记文件名由每个游戏的包装脚本自己传给内核：

- 零境：`crossingvoid` / `CrossingVoid.version.json`
- 幻杀：`fantasyproject` / `FantasyProject.version.json`
- 安卓产品段自动加 `-android`

内核做这些事：

| 步骤 | 做什么 |
|---|---|
| 1 | 按平台扫描产物。PC 排除 `.pdb`、`_download`、`.git`、`Saved\Logs|Crashes`、`Manifest_DebugFiles_Win64.txt`；安卓只发主 APK + OBB 里的每个条目，OBB 本体/AFS/符号/bat 不发 |
| 2 | 安卓把 OBB 解到暂存目录（`Expand-AndroidObb`），条目路径就是清单 path |
| 3 | 生成 **schemaVersion=1** 文件级清单：`productKey / runtime / version / channel / baseUrl / files[path,sizeBytes,sha256]` |
| 4 | 生成版本标记（2 空格 + CRLF + 无尾换行） |
| 5 | 安卓生成 `CrossingVoid.obb.json` 旁车（`obbFileName / entries / version / productKey`） |
| 6 | 本机暂存到 `F:\DaBaoV\下载站\<产品段>`；`game-file-sync.sh prepare` 在服务端从上版硬链接，只传变化文件 |
| 7 | `game-file-sync.sh finalize`：归档上一版、清掉清单外文件、写 `latest.json`；如果已有 `fragments/<版本>.json`，顺带写 `fragmentsUrl` |
| 8 | 公网校验清单 + HEAD 抽样；GitHub 备用渠道可选（`-GitHubRepo`，当前游戏包装脚本没传） |

服务端布局：

```
/srv/downloads/games/crossingvoid/
  0.6.0/...
  manifests/0.6.0.json
  latest.json
  fragments/0.6.0.json

/srv/downloads/games/crossingvoid-android/
  0.6.0/...
  manifests/0.6.0.json
  latest.json
  fragments/0.6.0.json
```

`latest.json` 是给启动器/AxTools 读“线上最新版”的：

```json
{"schemaVersion":1,"productSegment":"crossingvoid","version":"0.6.0",
 "manifestUrl":"...","generatedAt":"...","fragmentsUrl":"..."}
```

### 1.3 服务端更新（crossing-server）

入口：服务器页 → 游戏页签 → 服务端更新区。

代码链路：

```
ServerPage.xaml.cs
  → ServerPageViewModel（状态/动作）
  → ServerGitUpdateService
  → Scripts/Servers/Aliyun/Invoke-AliyunServerGit.ps1（远端）
  → Remote-AliyunServerGit.ps1（在阿里云 Windows 上执行）
  → Scripts/Servers/Aliyun/Invoke-AliyunServerRepo.ps1（本机仓库导入/提交/推送）
```

仓库形态（三个游戏共用一套）：

- 本机仓库：`D:\DabaoV\服务器Git合集\<本地目录名>`；
- 远端裸仓库：`C:\Users\Administrator\Desktop\ServerRepos\<repo>.git`；
- 外部工作树：就是线上运行目录；`Saved\` 排除，玩家数据不会被 checkout 覆盖；
- 看门狗配置：`C:\UEWatchdog\watchdog.config.psd1`；维护文件、端口、健康检查都从里面读。

| 实例 | `CrossingVoid-Login`、`CrossingVoid-Main` |
| 本地仓库目录 | `D:\DabaoV\服务器Git合集\零境交错` |
| 远端仓库 | `.../ServerRepos/crossingvoid.git` |
| 工作树 | `C:\Users\Administrator\Desktop\WindowsServer` |
| 端口 | 11451（登录大厅）/ 11452（主大厅） |

幻杀档案（已在 catalog 里）：

| 项 | 值 |
|---|---|
| Key | `fantasyproject` |
| 实例 | `FantasyProject` |
| 本地仓库目录 | `D:\DabaoV\服务器Git合集\幻杀` |

| 可执行文件 | `FantasyProjectServer.exe` |
| 端口 | 以 `watchdog.config.psd1` 为准 |

UI 动作顺序：

1. **导入新构建**：选源目录 → 镜像到本机仓库 → 显示差异；
2. **提交**：填写提交说明；
3. **推送新版本**：推裸仓库，服务端照常运行；
4. **切换最新版本**：暂挂看门狗 → 停服 → checkout → 启动 → 健康检查（最多 420 秒）→ 恢复看门狗；失败自动回退；
5. **回退上个版本**：同一套维护/健康流程。

零境的源目录不在仓库里，是用户在“导入新构建”时选的；幻杀对应 `F:\DaBaoV\Fantasy\WindowsServer`（当前构建）。`F:\DaBaoV\Fantasy\Server\WindowsServer` 是 8 月的旧副本，不要用。

### 1.4 碎片生成（零境）

入口：

- PC：TFAC启动平台页 → 碎片制作页签 → 零境碎片生成；
- 安卓：平台-零境-安卓页 → 碎片制作页签 → 碎片生成。

源目录直接复用「服务器 → 零境交错」游戏包发布的 PC/安卓目录，不在碎片制作里再选。

#### PC

1. 确保 `CrossingVoid.version.json`（Windows/stable）；
2. 扫打包目录，排除规则和发布内核一致；
3. 按路径 Ordinal 排序 + next-fit，每片 ≤ 1 GiB；
4. 清空输出目录（安全护栏：盘根/源目录/用户目录/链接都拒绝）；
5. 每片调 Bandizip `c -fmt:zip -l:5 -r -y`，写完 `t` 校验；
6. 写 `fragments.json`。

0.6.0 实测 3 片：862,273,823 / 846,465,935 / 951,699,870 B，40 / 75 / 64 条。

#### 安卓

1. 确保 Android 版本标记（优先下载线上，字节一致才复用）；
2. `CrossingVoidAndroidPackage.Locate`：定位 `main.*.obb` + 主 APK，排除 `AFS_*.apk`，读 OBB 中央目录 155 条；
3. `CrossingVoidAndroidObbSidecar` 按线上 PowerShell 格式生成 `CrossingVoid.obb.json`：
   - 8,796 B / sha256 `22cc73d4…`；
   - 2 空格 + CRLF + 无尾换行；
   - entries 按 `Sort-Object -CaseSensitive` 的文化顺序，不是 Ordinal；
4. 第 1 片安装包：APK + `CrossingVoid.version.json` + `CrossingVoid.obb.json`；
5. 后面的基础碎片：OBB 条目复用 `PlanBySize`；全部 Store，流式写 zip，不解 OBB 到临时目录；
6. 写 `fragments.json`（安装包第一）。

0.6.0 实测：

| 文件 | 原始字节 | 条目 |
|---|---:|---:|
| `零境V0.6安卓安装包.zip` | 75,993,488 | 3 |
| `零境V0.6安卓基础碎片001.zip` | 929,156,955 | 74 |
| `零境V0.6安卓基础碎片002.zip` | 1,008,557,303 | 57 |
| `零境V0.6安卓基础碎片003.zip` | 354,800,760 | 24 |

分片是 next-fit 的实际结果 886/962/338 MiB，不是简单三等分 ~730×3。

#### 碎片清单发布

`Publish-GameFragmentManifest.ps1`：

- 本地读 `fragments.json` 和 4 个 zip 的中央目录，核对大小/条目数；
- 只上传 `fragments.json`（几 KB）到下载站 `games/<产品段>/fragments/<版本>.json`；
- 更新 `latest.json` 的 `fragmentsUrl`；
- 公网只读校验；连续失败降级为警告（不误判发布失败）。

**zip 本身不上服务器**，走网盘/QQ 群。

#### 启动器怎么消费

零境安卓启动器：

- 玩家选一个放着 4 个 zip 的文件夹；
- `PackageFragmentImporter` 递归扫 zip，按**条目名**对线上清单；
- 逐条 `size + sha256` 校验，写到 APK/entries/prepared；
- 158 条全齐后 `ObbAssembler` 组装 STORED OBB，再走 APK 安装。

它不看 zip 文件名，只看条目名和哈希；所以 `CrossingVoid.obb.json` 必须和线上那份逐字节一致。

### 1.5 零境链路里哪些已经通用、哪些写死

| 层 | 现状 |
|---|---|
| 游戏包上传内核 | 已通用：`-ProductSegment / -Platform / -VersionMarkerName / -GitHubRepo`；幻杀适配器/包装脚本已有 |
| 服务端更新 | 已通用：catalog + 远端 watchdog 配置；幻杀已登记 |
| 碎片切片算法/执行器 | 算法本身通用；类名和调用点仍叫 `CrossingVoid*` |
| 版本标记 | JSON 格式通用；文件名、下载产品段、调用方写死 `CrossingVoid.version.json` |
| Android OBB 旁车 | JSON 格式/排序通用；文件名、productKey 写死 `CrossingVoid.obb.json` / `crossingvoid-android-game` |
| Android 产物定位 | APK/OBB 匹配规则本身通用；类名/标记名写死 |
| 包名前缀 | `零境V{主}.{次}{平台}` 写死在 `BuildArchiveNamePrefix` |
| 碎片 UI | `HasFragmentGeneration` 只认 `CrossingVoidPc` / `CrossingVoidAndroid`；描述/输出目录写死零境 |
| 碎片清单发布脚本 | 产品段已参数化；兜底/命名仍写死 `零境V…` |

### 2.2 已经具备的

- **服务端更新**：catalog、远端脚本、watchdog 配置都有 `fantasyproject`；动作与零境同一套。
- **游戏包上传**：`FantasyGameAdapter`、`Invoke-FantasyGameAction.ps1`、`FantasyGamePage` 都已接；产品段/标记名正确。
- **版本状态**：`CrossingVoidGamePublishState` 实际按三个游戏各建一份，幻杀的版本/渠道/线上检查有位置。
- **发布内核**：`Publish-GameDownloadRelease.ps1` 对任意产品段/标记名都适用，安卓 OBB 拆条目也适用。

### 2.3 关键缺口

1. **幻杀启动器格式没对齐**
   - 零境 Android 启动器读 schemaVersion=1 文件级清单 + zip 条目 + OBB 旁车；
   - 幻杀 Android 启动器 `src/services/gameUpdate.ts` 读 `https://www.crossingvoid.top/manifests/fantasyproject/game/android-latest.json`，要求 `schemaVersion=2`、`asset.chunks`、`FantasyProject手机端.碎片NNN` 整包分片；
   - `GameDownloadService.java` 也是按整包分片导入，没有 `PackageFragmentImporter` / `ObbAssembler`；
   - 所以 AxTools 现在按零境内核发出来的 v1 包，幻杀启动器**不会消费**。

2. **碎片链路完全没有幻杀**
   - `HasFragmentGeneration` 只认 `CrossingVoidPc` / `CrossingVoidAndroid`；
   - `FragmentProductSegment`、`FragmentArchiveNamePrefix`、默认输出目录、描述、`FragmentGameDirectory` 都写死零境；
   - `CrossingVoidVersionMarker`、`CrossingVoidAndroidObbSidecar`、`CrossingVoidAndroidFragmentPlanner` 写死标记名/旁车名/productKey；
   - `Publish-GameFragmentManifest.ps1` 的兜底和命名写死 `零境V…`。

3. **幻杀 PC 碎片没有页面**
   - `FantasyProjectPc` 在 catalog 里，但不在左侧导航，`MainWindow.xaml` 没有对应 `ToolPage`；
   - 设置里的 `D:\UnrealMap\FantasyProject-PC` 也不存在；
   - 碎片入口放哪需要先定。

4. **版本/变体未定**
   - 版本号空着；本地只有 0.1.1 的旧暂存；
   - Android 用新的 `Android` 还是当前配置的 `Android_ASTC`，会直接影响 OBB 大小/碎片内容。

5. **服务端源目录要确认**
   - 当前构建是 `F:\DaBaoV\Fantasy\WindowsServer`；`Server\WindowsServer` 是旧副本；
   - 远端工作树/端口要确认 `watchdog.config.psd1` 里 `FantasyProject` 的配置就是线上那套。

## 3. 通用化方案

### 3.1 先抽 `GameProfile`

不要直接把 `CrossingVoid*` 复制一份改名字；先定义一个游戏档案，所有游戏相关差异集中在这里：

| 字段 | 零境 | 幻杀 |
|---|---|---|
| Key / 产品段 | `crossingvoid` | `fantasyproject` |
| 显示名 | 零境交错：空界幻境 | 幻杀 |
| 短名（包名前缀） | 零境 | 幻杀 |
| 版本标记文件名 | `CrossingVoid.version.json` | `FantasyProject.version.json` |
| OBB 旁车文件名 | `CrossingVoid.obb.json` | `FantasyProject.obb.json` |
| Android APK 匹配 | `*-Android-Shipping-*.apk` | 同左 |
| OBB 匹配 | `main.*.obb` | 同左 |
| PC 源目录字段 | `GamePackageRoot` | 同左 |
| Android 源目录字段 | `GamePackageRootAndroid` | 同左 |
| 默认 PC 输出目录 | `D:\零境交错PC碎片` | `D:\幻杀PC碎片` |
| 默认安卓输出目录 | `D:\零境交错安卓碎片` | `D:\幻杀安卓碎片` |
| 服务端程序 Key | `crossingvoid` | `fantasyproject` |
| 碎片 PC/安卓页面 | `CrossingVoidPc/Android` | 待定（见问题 4） |
| 启动器清单格式 | v1 + zip/OBB 旁车 | 旧 v2 整包分片（是否迁移待定） |

### 3.2 服务层

建议保留行为，改通用命名/参数：

| 现在 | 通用化 |
|---|---|
| `CrossingVoidVersionMarker` | `GameVersionMarker`，参数化标记文件名/产品段 |
| `CrossingVoidAndroidObbSidecar` | `GameAndroidObbSidecar`，参数化旁车名/productKey |
| `CrossingVoidAndroidPackage` | `GameAndroidPackage`，参数化 APK/OBB 匹配 + 标记/旁车名 |
| `CrossingVoidAndroidFragmentPlanner` | `GameAndroidFragmentPlanner`，参数化 profile |
| `CrossingVoidAndroidFragmentExecutor` | 基本通用，可保留/改名 |
| `CrossingVoidFragmentGenerator/Planner/Executor` | PC 通用切片，改 `GameFragment*` |
| `CrossingVoidPackageInspector` | `GamePackageInspector`，参数化标记文件名；排除规则通用 |
| `BuildArchiveNamePrefix` | 加 `gameShortName` 参数，不再写死 `零境V` |
| `CrossingVoidFragmentManifestWriter` | 已通用，可保留 |

通用化的关键是**所有“名字”从 profile 来**，算法和 IO 不分游戏。

### 3.3 UI

- `ToolPageViewModel.Fragments` 改成从 profile 读：
  - `HasFragmentGeneration` = profile 支持碎片；
  - `FragmentProductSegment`、`FragmentChannel`、`FragmentProductKey`、`FragmentGameVersion`、`FragmentGameDirectory` 全部走 profile/注入的 game paths；
  - 默认输出目录用 profile 的显示名；
  - 描述和按钮文案用 profile。
- `ApplicationViewModel` 不要再只给 `CrossingVoidPc/Android` 注入 `gamePublishPaths`；按游戏把对应 `*Game` 的 `ManagedToolPaths` 注入给该游戏的碎片页。

### 3.5 启动器格式：两条路

**A. 迁移幻杀安卓启动器到零境同款（推荐做“真同等待遇”）**

- 读 `dl.crossingvoid.top` 的 schemaVersion=1 清单；
- 用 `GamePackagePlan` 同款解析；
- 玩家选文件夹 → 扫 zip → 按条目名对清单 → 验 sha256 → `ObbAssembler` 组装 OBB；
- 可以复用/移植零境的 `PackageFragmentImporter.java`、`ObbAssembler.java`、`GamePackagePlan.java`；
- 同时把游戏包下载从旧 schema v2 切到 v1；旧的 `www.crossingvoid.top/manifests/fantasyproject/game/android-latest.json` 退役；
- 工作量主要在启动器仓库，不在 AxTools。

**B. 先不迁启动器，AxTools 出旧格式（只做过渡）**

- 需要另写一个“幻杀旧分片”生成器：整包 zip 切片成 `FantasyProject手机端.碎片NNN` + APK/OBB，再生成旧 schema v2 清单；
- 和零境的新碎片是两套格式，无法“同等待遇”，只适合过渡；
- 不建议长期维护。

**C. AxTools 先按新格式出包，启动器后补**

- AxTools 侧通用化先做，幻杀碎片生成/发布先跑通；
- 启动器迁移另立项目；期间幻杀玩家暂时不能用新碎片（或手动解压/旧渠道）。
