# 零境安卓碎片 · 启动器对接说明

> 适用游戏版本：0.6.0（stable）
> 产物来源：AxTools《碎片生成》→ 安卓页
> 给：安卓启动器（CrossingVoidinitiator-Android）导入 / 组装 OBB 的同学
>
> 一句话：**产物从「一堆散件 + 旧三组压缩包」变成了「1 个安装包 + N 个基础碎片，共 4 个 zip」；启动器现有「选文件夹 → 扫 zip → 按条目名对清单 → 验 sha256 → 组装 OBB」的链路可以直接接，重点核对 `CrossingVoid.obb.json` 的字节和「不要按 zip 文件名判断内容」。**
>
> 核对（2026-10-19）：用 `D:\零境交错安卓碎片` 的 4 个 zip 对线上
> `manifests/0.6.0.json` 逐条比对 —— **158/158 条目名、大小、sha256 全部一致**，0 缺失、0 多余；
> `CrossingVoid.version.json` / `CrossingVoid.obb.json` 的字节与 sha256 也与清单一致。

## 1. 玩家拿到的文件

0.6.0 一版共 **4 个 zip + 1 个 `fragments.json`**：

| 文件 | 解压后总计 | zip 实际字节（= `sizeBytes`） | zip 内条目数 | 作用 |
|---|---:|---:|---:|---|
| `零境V0.6安卓安装包.zip` | 75,993,488 B | 75,993,908 B | 3 | 主 APK + `CrossingVoid.version.json` + `CrossingVoid.obb.json` |
| `零境V0.6安卓基础碎片001.zip` | 929,156,955 B | 929,169,297 B | 74 | OBB 条目 |
| `零境V0.6安卓基础碎片002.zip` | 1,008,557,303 B | 1,008,567,199 B | 57 | OBB 条目 |
| `零境V0.6安卓基础碎片003.zip` | 354,800,760 B | 354,804,876 B | 24 | OBB 条目 |
| `fragments.json` | — | 602 B | — | 4 个包的清单（给页面/下载器看，导入不依赖） |

四个 zip 全部 **STORED**（不压缩），所以「解压后总计」只比 zip 实际字节小一点点 —— 差的几百到
一万多字节是 zip 的目录/条目头开销，不是内容差异。**下载完整性看第二列**：文件实际字节必须等于
`fragments.json` 里的 `sizeBytes`；对不上就是没下完整（第一列是解压后的总和，拿来和清单总字节对）。

4 个 zip 的全部条目合起来是 **158 条**，逐字符等于线上清单 `games/crossingvoid-android/manifests/0.6.0.json` 的 158 个 `path`：

- 1 条主 APK：`CrossingVoid-Android-Shipping-arm64.apk`
- 155 条 OBB 条目：`CrossingVoid/Content/Paks/*`、`CrossingVoid/Content/Movies/*.mp4`、`Engine/...`
- `CrossingVoid.version.json`
- `CrossingVoid.obb.json`

**没有**：OBB 本体、符号目录、`AFS_*.apk`、安装/卸载 bat、`win-x64/` 工具。

## 2. 条目名规则（最重要）

1. **zip 内条目名就是清单里的相对路径**，原样，不套 `OBB/` 前缀，不改大小写，不转义。
2. 基础碎片里是 `CrossingVoid/...`、`Engine/...`；安装包里是三个平铺文件名：
   - `CrossingVoid-Android-Shipping-arm64.apk`
   - `CrossingVoid.version.json`
   - `CrossingVoid.obb.json`
3. zip 里不写目录条目，只有文件条目。
4. **不要按 zip 文件名判断里面是什么**。玩家可能重命名 zip；导入器必须按条目名对清单。
5. 安装包不一定叫“001”，它单独一张；基础碎片编号从 001 开始。启动器不要假设“001 一定是基础碎片”，也不要用编号拼内容。
6. **条目名大小写敏感**：清单是 `CrossingVoid/Content/Paks/...`，zip 里写成 `crossingvoid/...` 就对不上。匹配只做 `\`→`/`、去掉开头 `./` 和 `/`，不做大小写归一。
7. 玩家把 4 个 zip 解压成散件放进同一个文件夹，也能导入 —— 导入器先按相对路径匹配散件，再逐个开 zip。所以“不用解压”是给玩家的建议，不是硬要求。

## 3. 导入流程

现有启动器已经有这条链路，按下面的顺序核对即可。

### 3.1 入口

玩家把 4 个 zip 放进一个文件夹（例如 `Download/零境碎片`），点「导入游戏碎片」：

1. 启动器先拉 `fragments/<版本>.json`，弹出预检对话框，列出这一版应有的 4 个包；
2. 点「选择文件夹」走 SAF 目录树选择器，选完把文件夹里 zip 的名字和大小带回来，
   按名字+大小标成绿/黄/灰/红（**只比名字和大小，不打开压缩包**）；
3. 点「开始导入」用同一个 treeUri 启动导入，不会再弹一次选择器。

`PackageFragmentImporter` 接收的仍是 SAF 的目录树 URI，并递归扫描目录里的 `.zip`。如果要支持“直接多选 4 个 zip”，需要另外加 `OpenMultipleDocuments`，但**不是必须**——选文件夹已经够用。

### 3.2 对清单

**前提：第一次导入前必须成功刷新过一次清单。** 导入计划由前端 `buildAndroidGameDownloadPlan` 生成，
输入是 `fetchAndroidGamePackage()` 拉的 `latest.json` → `manifests/0.6.0.json` → `CrossingVoid.obb.json`。
拉不到时启动器会退回**上次成功拉到时缓存的清单**（`gamePackageCache.ts`，localStorage），
只有“从没成功拉到过”才会提示必须先刷新。缓存只服务导入/展示，**下载永远要求在线清单**。

- 清单来源：线上 `manifests/<版本>.json` → `GamePackagePlan`。
- 必须使用 `plan.manifestFiles`（全量 158 条），不是只用 `plan.files`（本次要下载的差异文件）。
  前端生成时 `manifestFiles: pkg.files` 就是清单全量；计划里缺这个字段的话，`GamePackagePlan`
  会退化成 `files`（差异集合），那种计划不能拿来导碎片。
- 对 zip 里的每个非目录条目：`name.replace('\\','/')`，去掉开头的 `./`、`/`，然后在 `manifestFiles`
  里按 path 精确匹配（**大小写敏感**，见第 2 节第 6 条）。
- 匹配不到 → 忽略（玩家文件夹里可能有别的东西）。
- 匹配到 → 写目标；目标已存在且 `size + sha256` 都对上 → 跳过（幂等）。

### 3.3 落点

沿用现有 `packageFileTarget` 的规则，不要另起一套：

| 清单条目类型 | 落点 |
|---|---|
| APK（`isApk`） | `prepared/CrossingVoid-latest.apk` |
| OBB 条目（`isObbEntry`） | `package-<版本>/entries/<path>` |
| 元数据（`CrossingVoid.version.json`、`CrossingVoid.obb.json`） | `prepared/<文件名>` |

`CrossingVoid.version.json` / `CrossingVoid.obb.json` 虽然组装 OBB 时不一定直接读（`GamePackagePlan` 里已经带了 `obb`），但它们**在清单里**，必须导入并校验；否则 `manifestFiles` 永远差两条，`isComplete()` 为 false。

### 3.4 组装 OBB

只有 158 条全部 `imported`、`missing`/`mismatched` 都为空，才进入组装：

- 用 `GamePackagePlan.obbFileName` 作为输出文件名；
- 用 `GamePackagePlan.obbEntries` 的顺序（来自线上 `CrossingVoid.obb.json` 的 `entries`）；
- 用现有 `ObbAssembler` 写 **STORED**（不压缩）ZIP；
- **zip comment 不是从旧 OBB 复制的**：`ObbAssembler` 从输出文件名里取 versionCode
  （`main.<versionCode>.<包名>.obb`），写成 `%10d` 右对齐的 10 字节 —— `main.1...` 就是
  10 个空格 + `1`。这段注释是 UE 判断「这是不是有效 OBB」的唯一依据，缺了会弹
  `No OBB found and no store key`，所以 **OBB 文件名里的 versionCode 必须和 APK 的 versionCode 一致**，
  不要手工改名。
- 条目来源：优先用这次导入的文件（`package-<版本>/entries/` 下），没导入的条目从**已安装的旧 OBB**
  里按同名原样搬；两处都没有就报错点名该条目。所以首次安装（没有旧 OBB）必须 155 条齐全才组装。
- 输出到 `getObbDir()/<obbFileName>`；组装成功后 `removeStaleObbFiles` 会删掉同目录里其它
  `main.*.obb` / `patch.*.obb`，别在那之后又手动放一份旧的回去。
- APK 走现有安装流程。

### 3.5 现有代码对照

| 现有实现 | 是否已满足 |
|---|---|
| `PackageFragmentImporter.importFrom` 扫目录、递归找 `.zip`、`ZipInputStream` 逐条读 | 是 |
| 按条目名对 `manifestFiles`，边拷边算 sha256 | 是 |
| `GameDownloadService` 的导入入口（约 898 行）调用 importer，再用 `preparePackageArtifacts` 组装 OBB | 是 |

## 4. 必须逐字节校验的文件

启动器导入时会按清单校验每一条的 `size + sha256`；下面三个是这次最容易踩的：

| 文件 | 0.6.0 大小 | sha256 | 说明 |
|---|---:|---|---|
| `CrossingVoid.obb.json` | 8,796 B | `22cc73d4a7cbe9156ab847800476c308d501464bea310cc6440a1813dd834d48` | 2 空格 + **CRLF** + 无结尾换行；entries 按 PowerShell 文化排序 |
| `CrossingVoid.version.json` | 76 B | `858486bdff47589d5b0428786dd1e4a67933d155437b59f7246be25fd52bcbf6` | 2 空格 + CRLF；`platform=Android`、`channel=stable` |
| `CrossingVoid-Android-Shipping-arm64.apk` | 75,984,616 B | `17fcd3f11e75674622de4dbf51aac24144dd15e7eb32cc005bceb7fa2f0386ea` | 原样拷贝，不要重签/改包 |

`CrossingVoid.obb.json` 的字段：

```json
{
  "obbFileName": "main.1.com.TFAC.CorssingVoid.obb",
  "entries": [ "CrossingVoid/...", "Engine/..." ],
  "version": "0.6.0",
  "productKey": "crossingvoid-android-game"
}
```

注意：

- `CorssingVoid` 是线上真实拼写（两个 s），不要“纠正”。
- `entries` 顺序不是 Ordinal；不要重排、不要重新序列化。启动器只读不写这份文件即可。
- Test 渠道的 `productKey` 是 `crossingvoid-android-game-test`；0.6.0 stable 用上面的值。
- 如果导入报 `CrossingVoid.obb.json` 内容对不上，先核对大小是不是 8,796 B；不是就让 AxTools 重新生成，不要手工改。

## 5. `fragments.json` 怎么用

它是给页面/下载器展示「这一版有几个包、每个包多大、装了多少条」的，**不是导入校验依据**。

线上实际内容（0.6.0，`fragments/0.6.0.json`）：

```json
{
  "schemaVersion": 1,
  "version": "0.6.0",
  "totalBytes": 2368535280,
  "fragments": [
    { "fileName": "零境V0.6安卓安装包.zip", "sizeBytes": 75993908, "fileCount": 3 },
    { "fileName": "零境V0.6安卓基础碎片001.zip", "sizeBytes": 929169297, "fileCount": 74 },
    { "fileName": "零境V0.6安卓基础碎片002.zip", "sizeBytes": 1008567199, "fileCount": 57 },
    { "fileName": "零境V0.6安卓基础碎片003.zip", "sizeBytes": 354804876, "fileCount": 24 }
  ]
}
```

- `totalBytes` 和 `sizeBytes` 都是 **zip 实际字节**；安卓四个包全部 Store，所以和「解压后总计」只差 zip 头开销。
- `fileCount` 是 zip 内文件条目数，不含目录。
- 没有 sha256（整包几 GB 算一遍太慢，而且导入时每个文件本来就要过 sha256）。
- 安装包识别：`fileName` 含 `安装包`；基础碎片含 `基础碎片`。但**只用于 UI 展示**，不要用它替代清单校验。
- `fragments.json` 不进 zip，放在下载文件夹/服务端清单目录即可；文件编码 UTF-8 无 BOM。
- **安卓启动器从 2026-10-19 起会读它**（导入预检对话框，`src/services/gameFragmentManifest.ts`）：
  按名字+大小把选中的 zip 标成绿/黄/灰，改名但大小唯一也能认；清单拉不到就退化成
  「直接选文件夹、导入后判齐」，不会挡住导入。

## 6. 失败、幂等、取消

- **缺文件**：`PackageFragmentImporter.Result.missing`；提示“碎片还不齐：缺 N 个（前三个路径）”，不要组装 OBB。
- **内容对不上**：`mismatched`；提示“有 N 个内容对不上”，常见原因是下载了旧版 AxTools 产物，`CrossingVoid.obb.json` 不是 8,796 B。
- **幂等**：已存在且 size+sha256 对上的文件跳过；玩家补一个包再点一次，不会重拷已对上的。
- **取消/暂停**：已完成的文件保留；临时文件用 `.importing` 后缀，下次覆盖。不要留下半成品 OBB（`ObbAssembler` 已有 `.assembling` 临时文件逻辑）。
- **坏 zip**：一个包读坏（下坏 / 没下完整 / 不是 zip / 空包 / 条目 CRC 不对）只跳过并记进 `brokenArchives`，
  其余包照常导入，包里没进来的文件按缺失算；提示会点名坏包并建议重下。写目标失败（磁盘满 / 没权限）仍然整单停，
  不会被当成“源坏了”吞掉。已经导入的文件保留，重试可继续。
- **先散件后 zip**：导入器先扫选中目录里的非 zip 文件（按相对路径对清单），再逐个开压缩包；
  同一个条目只处理一次 —— 玩家把包解压了也能导。
- **同一个 path 出现在两个包里**：只有先命中的那次生效，后面的静默跳过，不报错。
- **路径归一**：只做 `\`→`/`、去掉开头 `./` 和 `/`，**不统一大小写**。
- **进度分母是 158**：导入进度按 `manifestFiles` 总数算，不是按当前包里的条目数。

## 9. 建议的实测用例

1. **正常导入**：4 个 zip 放同一文件夹 → 选文件夹 → 158/158 → OBB 组装成功 → 安装 APK → 启动。
2. **缺包**：删掉 `基础碎片002.zip` → 报缺 57 条左右；补回再点一次 → 只补缺的，不重拷已对上的。
3. **坏旁车**：用旧版 AxTools 生成的 `CrossingVoid.obb.json`（不是 8,796 B）→ 报 1 条内容对不上；换成本次产物 → 通过。
4. **重命名**：把 `零境V0.6安卓基础碎片001.zip` 改名成 `001.zip` → 仍能导入（条目名没变）。
5. **混入杂物**：文件夹里放一张图片/一个无关 zip → 忽略，不影响 158 条匹配。
6. **取消**：导入到一半暂停 → 已导入文件保留；再点继续 → 不重拷已对上的；不生成半成品 OBB。
7. **Test 渠道**（如果后续出 Test 包）：productKey 应为 `crossingvoid-android-game-test`，version.json 的 `channel` 为 `test`；不要拿 stable 的哈希去对 Test 包。
8. **解压成散件**：把 4 个 zip 解压到同一个文件夹 → 选文件夹 → 158/158（散件优先匹配，连 zip 都不用开）。
9. **断网导入（有缓存）**：先联网刷新成功一次，再断网冷启动 → 「游戏管理」显示使用缓存清单，直接导入仍 158/158，OBB 组装成功。
10. **断网导入（无缓存）**：全新安装、从没刷新过、断网 → 提示「还没拿到游戏清单，先刷新一次状态再导入碎片」；联网刷新后正常。
11. **OBB 注释**：组装完成后看 OBB 末尾 EOCD 的 comment，应是 `%10d` 的 versionCode（`main.1...` → 10 个空格 + `1`）；缺了 UE 会报 `No OBB found and no store key`。
12. **坏包**：把 `零境V0.6安卓基础碎片001.zip` 改坏（或只下到一半）→ 导入跳过它并提示“有 1 个压缩包打不开”，002/003 照常导入；补回完整 001 再导一次，只补缺的 74 条，不重拷。
13. **预检**：只放安装包 + 001 → 对话框里 002/003 标灰、提示还差 2 个；补进 002/003 再选同一文件夹 → 4 个全绿。

## 10. 和 AxTools 的边界
