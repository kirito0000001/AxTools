# 零境安卓碎片 · 启动器对接说明

> 适用游戏版本：0.6.0（stable）
> 产物来源：AxTools《碎片生成》→ 安卓页
> 给：安卓启动器（CrossingVoidinitiator-Android）导入 / 组装 OBB 的同学
>
> 一句话：**产物从「一堆散件 + 旧三组压缩包」变成了「1 个安装包 + N 个基础碎片，共 4 个 zip」；启动器现有「选文件夹 → 扫 zip → 按条目名对清单 → 验 sha256 → 组装 OBB」的链路可以直接接，重点核对 `CrossingVoid.obb.json` 的字节和「不要按 zip 文件名判断内容」。**

## 1. 玩家拿到的文件

0.6.0 一版共 **4 个 zip + 1 个 `fragments.json`**：

| 文件 | 大小（原始） | zip 内条目数 | 作用 |
|---|---:|---:|---|
| `零境V0.6安卓安装包.zip` | 75,993,488 B | 3 | 主 APK + `CrossingVoid.version.json` + `CrossingVoid.obb.json` |
| `零境V0.6安卓基础碎片001.zip` | 929,156,955 B | 74 | OBB 条目 |
| `零境V0.6安卓基础碎片002.zip` | 1,008,557,303 B | 57 | OBB 条目 |
| `零境V0.6安卓基础碎片003.zip` | 354,800,760 B | 24 | OBB 条目 |
| `fragments.json` | 几 KB | — | 4 个包的清单（给页面/下载器看，导入不依赖） |

4 个 zip 的全部条目合起来是 **158 条**，逐字符等于线上清单 `games/crossingvoid-android/manifests/0.6.0.json` 的 158 个 `path`：

- 1 条主 APK：`CrossingVoid-Android-Shipping-arm64.apk`
- 155 条 OBB 条目：`CrossingVoid/Content/Paks/*`、`CrossingVoid/Content/Movies/*.mp4`、`Engine/...`
- `CrossingVoid.version.json`
- `CrossingVoid.obb.json`

**没有**：OBB 本体、符号目录、`AFS_*.apk`、安装/卸载 bat、`win-x64/` 工具。

## 2. 条目名规则（最重要）

1. **zip 内条目名就是清单里的相对路径**，原样，不套 `OBB/` 前缀，不改大小写，不转义。
2. 基础碎片里是 `CrossingVoid/...`、`Engine/...`；安装包里是三个平铺文件名：
   - `CrossingVoid-Android-Shipping-arm64.apk`
   - `CrossingVoid.version.json`
   - `CrossingVoid.obb.json`
3. zip 里不写目录条目，只有文件条目。
4. **不要按 zip 文件名判断里面是什么**。玩家可能重命名 zip；导入器必须按条目名对清单。
5. 安装包不一定叫“001”，它单独一张；基础碎片编号从 001 开始。启动器不要假设“001 一定是基础碎片”，也不要用编号拼内容。

## 3. 导入流程

现有启动器已经有这条链路，按下面的顺序核对即可。

### 3.1 入口

玩家把 4 个 zip 放进一个文件夹（例如 `Download/零境碎片`），在启动器里选这个文件夹。

当前 `PackageFragmentImporter` 接收的是 SAF 的目录树 URI；它会递归扫描目录里的 `.zip`。如果要支持“直接多选 4 个 zip”，需要另外加 `OpenMultipleDocuments`，但**不是必须**——选文件夹已经够用。

### 3.2 对清单

- 清单来源：线上 `manifests/<版本>.json` → `GamePackagePlan`。
- 必须使用 `plan.manifestFiles`（全量 158 条），不是只用 `plan.files`（本次要下载的差异文件）。碎片导入的场景下两者应覆盖同一批 path。
- 对 zip 里的每个非目录条目：`name.replace('\\','/')`，去掉开头的 `./`、`/`，然后在 `manifestFiles` 里按 path 精确匹配。
- 匹配不到 → 忽略（玩家文件夹里可能有别的东西）。
- 匹配到 → 写目标；目标已存在且 `size + sha256` 都对上 → 跳过（幂等）。

### 3.3 落点

沿用现有 `packageFileTarget` 的规则，不要另起一套：

| 清单条目类型 | 落点 |
|---|---|
| APK（`isApk`） | `prepared/CrossingVoid-latest.apk` |
| OBB 条目（`isObbEntry`） | `package-<版本>/entries/<path>` |
| 元数据（`CrossingVoid.version.json`、`CrossingVoid.obb.json`） | `prepared/<文件名>` |

`CrossingVoid.version.json` / `CrossingVoid.obb.json` 虽然组装 OBB 时不一定直接读（`GamePackagePlan` 里已经带了 `obb`），但它们**在清单里**，必须导入并校验；否则 `manifestFiles` 永远差两条，`isComplete()` 为 false。

### 3.4 组装 OBB

只有 158 条全部 `imported`、`missing`/`mismatched` 都为空，才进入组装：

- 用 `GamePackagePlan.obbFileName` 作为输出文件名；
- 用 `GamePackagePlan.obbEntries` 的顺序（来自线上 `CrossingVoid.obb.json` 的 `entries`）；
- 用现有 `ObbAssembler` 写 **STORED**（不压缩）ZIP；
- 尽量保留已安装 OBB 的 zip comment（UE 的 OBB 版本号）；首次安装没有旧 OBB 时按现有逻辑给默认值；
- 输出到 `getObbDir()/<obbFileName>`；
- APK 走现有安装流程。

### 3.5 现有代码对照

| 现有实现 | 是否已满足 |
|---|---|
| `PackageFragmentImporter.importFrom` 扫目录、递归找 `.zip`、`ZipInputStream` 逐条读 | 是 |
| 按条目名对 `manifestFiles`，边拷边算 sha256 | 是 |
| `GameDownloadService` 的导入入口（约 898 行）调用 importer，再用 `preparePackageArtifacts` 组装 OBB | 是 |
| `packageFileTarget` 把 APK/OBB 条目/元数据分到 prepared / entries | 是 |
| `ObbAssembler` STORED 组装、保留 comment | 是 |
| 旧注释里写的「分片 / 影片包 / 其余文件包」三种形态 | **已过时**，需要更新注释，但代码逻辑本身兼容新形态 |
| 旧逻辑是否依赖 `CrossingVoid手机端.碎片NNN` 这类 zip 名 | **不能依赖**；新产物不生成这些名字，导入只看条目名 |

## 4. 必须逐字节校验的文件

启动器导入时会按清单校验每一条的 `size + sha256`；下面三个是这次最容易踩的：

| 文件 | 0.6.0 大小 | sha256 | 说明 |
|---|---:|---|---|
| `CrossingVoid.obb.json` | 8,796 B | `22cc73d4a7cbe9156ab847800476c308d501464bea310cc6440a1813dd834d48` | 2 空格 + **CRLF** + 无结尾换行；entries 按 PowerShell 文化排序 |
| `CrossingVoid.version.json` | 76 B | `858486bdff47589d5b0428786dd1e4a67933d155437b59f7246be25fd52bcbf6` | 2 空格 + CRLF；`platform=Android`、`channel=stable` |
| `CrossingVoid-Android-Shipping-arm64.apk` | 75,984,616 B | `17fcd3f11e75674622de4dbf51aac24144dd15e7eb32cc005bceb7fa2f0386ea` | 原样拷贝，不要重签/改包 |

`CrossingVoid.obb.json` 的字段：

```json
{
  "obbFileName": "main.1.com.TFAC.CorssingVoid.obb",
  "entries": [ "CrossingVoid/...", "Engine/..." ],
  "version": "0.6.0",
  "productKey": "crossingvoid-android-game"
}
```

注意：

- `CorssingVoid` 是线上真实拼写（两个 s），不要“纠正”。
- `entries` 顺序不是 Ordinal；不要重排、不要重新序列化。启动器只读不写这份文件即可。
- Test 渠道的 `productKey` 是 `crossingvoid-android-game-test`；0.6.0 stable 用上面的值。
- 如果导入报 `CrossingVoid.obb.json` 内容对不上，先核对大小是不是 8,796 B；不是就让 AxTools 重新生成，不要手工改。

## 5. `fragments.json` 怎么用

它是给页面/下载器展示「这一版有几个包、每个包多大、装了多少条」的，**不是导入校验依据**。

下面只示意字段，数值以实际 `fragments.json` 为准（`sizeBytes` 是压缩后字节，不是上面的原始字节）：

```json
{
  "schemaVersion": 1,
  "version": "0.6.0",
  "totalBytes": 2361000000,
  "fragments": [
    { "fileName": "零境V0.6安卓安装包.zip", "sizeBytes": 75993488, "fileCount": 3 },
    { "fileName": "零境V0.6安卓基础碎片001.zip", "sizeBytes": 929160000, "fileCount": 74 }
  ]
}
```

- `totalBytes` 和 `sizeBytes` 都是 **zip 压缩后**的字节；安卓全部 Store，约等于原始大小。
- `fileCount` 是 zip 内文件条目数，不含目录。
- 没有 sha256。
- 安装包识别：`fileName` 含 `安装包`；基础碎片含 `基础碎片`。但**只用于 UI 展示**，不要用它替代清单校验。
- `fragments.json` 不进 zip，放在下载文件夹/服务端清单目录即可。

## 6. 失败、幂等、取消

- **缺文件**：`PackageFragmentImporter.Result.missing`；提示“碎片还不齐：缺 N 个（前三个路径）”，不要组装 OBB。
- **内容对不上**：`mismatched`；提示“有 N 个内容对不上”，常见原因是下载了旧版 AxTools 产物，`CrossingVoid.obb.json` 不是 8,796 B。
- **幂等**：已存在且 size+sha256 对上的文件跳过；玩家补一个包再点一次，不会重拷已对上的。
- **取消/暂停**：已完成的文件保留；临时文件用 `.importing` 后缀，下次覆盖。不要留下半成品 OBB（`ObbAssembler` 已有 `.assembling` 临时文件逻辑）。
- **坏 zip**：一个 zip 读失败不应影响其他 zip 已导入的文件；当前实现会抛异常并终止本次导入，已导入的文件仍在，重试可继续。如果想更宽容，可以改成“跳过坏包、继续其他包”，这是可选优化。

## 7. 对接检查清单

- [ ] 产物是 4 个 zip，不再生成旧的「影片包 / 其余文件包」。
- [ ] 导入器递归扫 `.zip`，按条目名对 `manifestFiles`，不按 zip 文件名。
- [ ] `manifestFiles` 是 158 条全量，不是本次差异文件。
- [ ] 元数据 `CrossingVoid.version.json` / `CrossingVoid.obb.json` 也导入、也验 sha256。
- [ ] APK / OBB 条目 / 元数据落点和下载链路一致（`packageFileTarget`）。
- [ ] 只有 `missing`/`mismatched` 都为空才组装 OBB。
- [ ] OBB 用 `plan.obbFileName`、`plan.obbEntries` 顺序、STORED；保留 comment。
- [ ] APK 用现有安装流程。
- [ ] 导入不依赖 `fragments.json`。
- [ ] 玩家重命名 zip 后仍能导入。
- [ ] 0.6.0 实测：158/158，报错为 0；OBB 生成成功；APK 可安装启动。

## 9. 建议的实测用例

1. **正常导入**：4 个 zip 放同一文件夹 → 选文件夹 → 158/158 → OBB 组装成功 → 安装 APK → 启动。
2. **缺包**：删掉 `基础碎片002.zip` → 报缺 57 条左右；补回再点一次 → 只补缺的，不重拷已对上的。
3. **坏旁车**：用旧版 AxTools 生成的 `CrossingVoid.obb.json`（不是 8,796 B）→ 报 1 条内容对不上；换成本次产物 → 通过。
4. **重命名**：把 `零境V0.6安卓基础碎片001.zip` 改名成 `001.zip` → 仍能导入（条目名没变）。
5. **混入杂物**：文件夹里放一张图片/一个无关 zip → 忽略，不影响 158 条匹配。
6. **取消**：导入到一半暂停 → 已导入文件保留；再点继续 → 不重拷已对上的；不生成半成品 OBB。
7. **Test 渠道**（如果后续出 Test 包）：productKey 应为 `crossingvoid-android-game-test`，version.json 的 `channel` 为 `test`；不要拿 stable 的哈希去对 Test 包。

## 10. 和 AxTools 的边界

- 碎片 zip 的生成、`CrossingVoid.obb.json` 的字节、158 条条目名，由 AxTools 负责。
- zip 的下载/网盘分发、玩家文件夹选择、导入落点、OBB 组装、APK 安装，由启动器负责。
- 如果启动器发现某条 path/size/sha 对不上，先查是不是用了旧版 AxTools 生成的包；确认是 AxTools 的问题，再把 `fragments.json`、出错 path、期望/实际 sha256 发回来。
