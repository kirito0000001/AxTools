# 零境碎片分发（PC + 安卓）

> 最后更新：2026-10-19
> 范围：AxTools 里的《生成碎片》《发布碎片清单》，以及它们和下载站、启动器之间的数据契约。
> 安卓启动器侧的独立对接说明见 `docs/安卓碎片-启动器对接.md`。

## 1. 它解决什么问题

零境的游戏包直接发网盘/QQ 群会有两个问题：文件太散、目录太深，玩家不知道该拿哪些；网盘/群对单文件大小、视频文件又有各种限制。

碎片把一版拆成几个独立的 zip，玩家不需要合并；同时在服务器上放一份 `fragments.json`，让启动器/页面提前知道「这一版有几个包、每个包多大、装了多少文件」。

- **PC**：扫打包目录，按压缩前体积切 3 片左右；每片一个独立 zip，全部解压到游戏安装目录即可。
- **安卓**：散件在 OBB 里，玩家手动解压装不了；AxTools 从 OBB 读条目 + 主 APK，切成「1 个安装包 + N 个基础碎片」，交给启动器导入组装 OBB。
- **碎片 zip 本身不上服务器**，只走网盘/QQ 群；服务器上只有几 KB 的清单。

## 2. 最终产物

### 2.1 PC（0.6.0 实测）

输出目录默认 `D:\零境交错PC碎片`：

| 文件 | 压缩前 | 压缩后 | 条目数 |
|---|---:|---:|---:|
| `零境V0.6PC基础碎片001.zip` | 954.5 MiB | 862,273,823 B | 40（含版本标记） |
| `零境V0.6PC基础碎片002.zip` | 841.8 MiB | 846,465,935 B | 75 |
| `零境V0.6PC基础碎片003.zip` | 940.9 MiB | 951,699,870 B | 64 |
| `fragments.json` | — | 约 0.5 KB | 描述上面三个包 |

zip 内部保持游戏目录树（`CrossingVoid/...`、`Engine/...`），解压到同一个安装目录即可还原。

### 2.2 安卓（0.6.0 实测）

输出目录默认 `D:\零境交错安卓碎片`：

| 文件 | 原始字节 | 条目数 | 内容 |
|---|---:|---:|---|
| `零境V0.6安卓安装包.zip` | 75,993,488 | 3 | 主 APK + `CrossingVoid.version.json` + `CrossingVoid.obb.json` |
| `零境V0.6安卓基础碎片001.zip` | 929,156,955（886.1 MiB） | 74 | OBB 条目 |
| `零境V0.6安卓基础碎片002.zip` | 1,008,557,303（961.8 MiB） | 57 | OBB 条目 |
| `零境V0.6安卓基础碎片003.zip` | 354,800,760（338.4 MiB） | 24 | OBB 条目 |
| `fragments.json` | — | 4 | 描述上面四个包，安装包排第一 |

安卓的 155 条 OBB 条目 = 122 条 `pak/ucas/utoc` + 29 条 `mp4` + 4 条 `Engine/...`；OBB 本体 `main.1.com.TFAC.CorssingVoid.obb` 是 2,292,541,338 B（注意 `CorssingVoid` 是线上真实拼写）。

> 分片按「路径 Ordinal 排序 + next-fit + 每片 ≤ 1 GiB」，和 PC 同一套 `PlanBySize`。因此三片是 886/962/338 MiB，不是简单三等分的 ~730×3；这是 next-fit 在这批大 pak 上的实际结果。如果以后要三片更均匀，需要单独换均衡算法，不能只改常量。

## 3. 数据契约

### 3.1 `fragments.json`

生成时写在碎片输出目录根；发布时上传为 `<版本>.json`。PC 和安卓共用同一份 schema。

```json
{
  "schemaVersion": 1,
  "version": "0.6.0",
  "totalBytes": 2660439628,
  "fragments": [
    {
      "fileName": "零境V0.6PC基础碎片001.zip",
      "sizeBytes": 862273823,
      "fileCount": 40
    }
  ]
}
```

| 字段 | 含义 |
|---|---|
| `schemaVersion` | 固定 1 |
| `version` | 完整游戏版本（`0.6.0`），来自「服务器 → 零境交错」的游戏版本 |
| `totalBytes` | 所有碎片 **压缩后** 字节和 |
| `fragments[].fileName` | zip 文件名，和玩家下载到的名字一致；安卓安装包排第一 |
| `fragments[].sizeBytes` | zip **压缩后** 实际大小 |
| `fragments[].fileCount` | zip 内文件条目数（不含目录条目） |

**故意不放 sha256**：整包几 GB 算一遍要十几秒，而启动器导入时每个文件本来就要过 sha256，包坏了必然当场暴露。`fileCount` 只读 zip 中央目录就有，几十毫秒，够判断「是不是同一个包」。

`fragments.json` 是给页面/下载器展示和核对包用的；**启动器导入不依赖它**，导入依据是线上游戏清单（158 条 path + size + sha256）。

### 3.2 安卓的两个旁车

安装包里带两个小文件，名字和内容都必须和线上发布目录里的那份**逐字节一致**——启动器会按清单校验它们的 sha256。

#### `CrossingVoid.version.json`

0.6.0 / Android / stable 是 **76 B**，sha256 `858486bdff47589d5b0428786dd1e4a67933d155437b59f7246be25fd52bcbf6`：

```json
{
  "version": "0.6.0",
  "platform": "Android",
  "channel": "stable"
}
```

字节格式：2 空格缩进、CRLF、无结尾换行、UTF-8 无 BOM。

#### `CrossingVoid.obb.json`

0.6.0 是 **8,796 B**，sha256 `22cc73d4a7cbe9156ab847800476c308d501464bea310cc6440a1813dd834d48`：

```json
{
  "obbFileName": "main.1.com.TFAC.CorssingVoid.obb",
  "entries": [
    "CrossingVoid/Content/Movies/...",
    "CrossingVoid/Content/Paks/...",
    "Engine/..."
  ],
  "version": "0.6.0",
  "productKey": "crossingvoid-android-game"
}
```

- `entries` 是 155 条 OBB 条目，顺序按 PowerShell `Sort-Object -Property Relative -CaseSensitive`（文化排序，不是 Ordinal；`_Low` 会排在无后缀的前面）。
- 格式：2 空格缩进、**CRLF**、无结尾换行。
- stable 的 `productKey` 是 `<产品段>-game`；Test 是 `<产品段>-game-test`。
- 这份文件必须和发布脚本生成的那份字节一致，不能在本地重新格式化/重新排序；AxTools 的 `CrossingVoidAndroidObbSidecar` 已按同样规则手写，0.6.0 的输出正好是 8,796 B / `22cc73d4…`。

### 3.3 服务端位置

PC：

```
/srv/downloads/games/crossingvoid/fragments/0.6.0.json
/srv/downloads/games/crossingvoid/latest.json          # 加 fragmentsUrl
```

安卓：

```
/srv/downloads/games/crossingvoid-android/fragments/0.6.0.json
/srv/downloads/games/crossingvoid-android/latest.json  # 加 fragmentsUrl
```

公网：

```
https://dl.crossingvoid.top/games/crossingvoid/fragments/0.6.0.json
https://dl.crossingvoid.top/games/crossingvoid-android/fragments/0.6.0.json
```

`latest.json` 里新增的字段：

```json
"fragmentsUrl": "https://dl.crossingvoid.top/games/crossingvoid-android/fragments/0.6.0.json"
```

### 3.4 命名规则

```
零境V{主}.{次}{平台}基础碎片{三位序号}.zip
零境V{主}.{次}{平台}安装包.zip          # 仅安卓
例：零境V0.6PC基础碎片001.zip
    零境V0.6安卓基础碎片001.zip
    零境V0.6安卓安装包.zip
```

- 版本只取主/次版：`0.6.0` → `V0.6`；`0.0.x` 是补丁，补丁之后单独出包，不混进基础碎片。
- 平台字样 `PC` / `安卓` 必须带：PC 和安卓的包名、清单、下载页要分得清。
- 不放短横线/空格，避免平台对文件名的限制。
- 前缀规则在 `CrossingVoidFragmentPlanner.BuildArchiveNamePrefix`，只改这一处就能改全链路。

## 4. 生成链路

### 4.1 PC

入口：PC 页（TFAC启动平台）→ **碎片制作**页签 → **零境碎片生成**。

| 步骤 | 代码 | 做什么 |
|---|---|---|
| 1 | `ToolPageViewModel.Fragments.cs` | 读版本、目录、渠道；拼 `零境V0.6PC` 前缀；按钮可用性 |
| 2 | `MainWindow.Fragments.cs` | 校验目录、确保版本标记、构建分片计划、确认弹窗 |
| 3 | `CrossingVoidVersionMarker` | 补齐 `CrossingVoid.version.json`（Windows/stable） |
| 4 | `CrossingVoidFragmentGenerator.ScanPackageFiles` | 递归扫描，排除 `.pdb` / `_download` / `.git` / `Saved\Logs|Crashes` / `Manifest_DebugFiles_Win64.txt` |
| 5 | `CrossingVoidFragmentPlanner.PlanBySize` | 路径 Ordinal 排序，next-fit，每片 ≤ 1024 MiB；同时算 Bandizip 命令行预算（28000 字符） |
| 6 | `CrossingVoidFragmentOutputCleaner.Clear` | 生成前清空输出目录 |
| 7 | `CrossingVoidFragmentExecutor.ExecuteSizeSlices` | 每片调一次 Bandizip，`c -fmt:zip -l:5 -r -y` + `t` 校验 |
| 8 | `CrossingVoidFragmentManifestWriter.Write` | 写 `fragments.json` |

### 4.2 安卓

入口：平台-零境-安卓 → **碎片制作**页签 → **碎片生成**。

| 步骤 | 代码 | 做什么 |
|---|---|---|
| 1 | `ToolPageViewModel.Fragments.cs` | 读版本、目录、渠道；拼 `零境V0.6安卓` 前缀；`productKey` 按渠道派生 |
| 2 | `CrossingVoidVersionMarker.EnsureAsync` | 补齐 Android 版本标记（优先下载线上那份，字节一致才复用） |
| 3 | `CrossingVoidAndroidPackage.Locate` | 定位 `main.*.obb` 和主 APK（排除 `AFS_*.apk`），读 OBB 中央目录 155 条 |
| 4 | `CrossingVoidAndroidObbSidecar.Build` | 按线上 PowerShell 格式生成 `CrossingVoid.obb.json` 字节 |
| 5 | `CrossingVoidAndroidFragmentPlanner.Build` | 第 1 片安装包（APK + version + obb.json）；OBB 条目复用 `PlanBySize` |
| 6 | `CrossingVoidFragmentOutputCleaner.Clear` | 生成前清空输出目录 |
| 7 | `CrossingVoidAndroidFragmentExecutor.Execute` | 不解 OBB 到临时目录，直接从 OBB 条目流式写新 zip；全部 Store；按条目报进度；取消/失败删当前半成品 |
| 8 | `CrossingVoidFragmentManifestWriter.Write` | 写 `fragments.json`（4 个包，安装包第一） |

技术要点：

- **不解 OBB 到临时目录**：Bandizip 只能打磁盘文件，先解 2.29 GB 会多占一份空间；直接用 `System.IO.Compression.ZipArchive` 从 OBB 条目流式拷贝到新 zip（`CompressionLevel.NoCompression`），零临时文件、可报进度、可取消。
- **条目名不套 `OBB/` 前缀**：导入器按清单 path 匹配，套一层就等于空包。安装包/基础碎片里的条目名就是清单里的 158 条 path，一条不多一条不少。
- **安装包片固定第一张**：APK 76 MB，装 APK 不需要先下 1 GB；签名校验也要求 APK 原样。
- **APK/OBB 条目原样拷贝**：启动器按清单逐条验 size + sha256；0.6.0 的 APK 和 155 条 OBB 条目已用线上清单逐条核对，0 条不符。

### 4.3 分片规则

- 按**压缩前**原始体积算，每片 ≤ 1024 MiB；
- 按路径 Ordinal 排序后顺序装箱（next-fit），结果稳定、可对拍；
- 单文件超过 1 GiB 时自己占一片，确认弹窗会提示「超限文件」；
- PC 的影片不再单独打包，跟其他文件一起切；安卓的 29 条 mp4 也按路径顺序进基础碎片，不单独拆。

### 4.4 清空输出目录

这是用户明确要求的行为：每次生成前清空 `FragmentOutputDirectory` 的内容，避免旧散件/旧包和新碎片混在一起。

安全护栏在 `CrossingVoidFragmentOutputCleaner.Validate`：

- 盘根 → 拒绝；
- 输出目录在源目录内部 / 是源目录上级 → 拒绝（防删源）；
- 用户目录（Profile / Desktop / Documents / Downloads / Pictures / Music / Videos / AppData）→ 拒绝；
- 输出目录本身是符号链接/联接点 → 拒绝；
- 只删内容，保留输出目录本身；只读文件先清属性。

确认弹窗会显示「清空输出目录：N 个文件 · X GB」，并加粗提示不可恢复。

## 5. 发布链路

入口：两个**碎片制作**页签都有 **发布碎片清单**。

### 5.1 前端

`MainWindow.FragmentManifestPublish.cs`：

- PC 页和安卓页都订阅 `FragmentManifestPublishRequested`；
- 校验输出目录、版本、清单/包存在；
- 走 `TaskRunner` 执行 `Scripts/Publishing/Games/Publish-GameFragmentManifest.ps1`；
- 参数：`-FragmentDirectory <输出目录> -ReleaseVersion <版本> -ProductSegment <crossingvoid|crossingvoid-android>`；
- 进度/日志复用 `TaskRunner_EventReceived`；`HostedTaskKind.GameFragmentManifestPublish`。

按钮可用性（`CanPublishFragmentManifest`）：
**`fragments.json` 存在，或目录里有 `零境V{主}.{次}{平台}基础碎片*.zip`** —— 后者允许旧包补清单。

### 5.2 脚本

`Publish-GameFragmentManifest.ps1`：

1. 读 `fragments.json`；**没有就按现有 zip 重建**（读中央目录、写回本地），不要求重新压几 GB；
2. 兜底 pattern 兼容 PC/安卓命名：`零境V${displayVersion}*基础碎片*.zip`；安卓额外找 `零境V${displayVersion}*安装包*.zip`，安装包排第一；多个安装包会报错；
3. 逐个校验 zip 存在、大小、包内条目数（只读中央目录，不解压）；
4. 默认把仓库里的 `game-file-sync.sh` 同步到 `/srv/scripts/`（hash 不同才传，`chmod 755`）；
5. 只上传 `fragments.json` 到 `/srv/downloads/games/<产品段>/fragments/<版本>.json`（先 `.axtmp` 再原子改名）；
6. 通过 ssh 读 `latest.json`，加/改 `fragmentsUrl`，再原子写回；
7. 公网 GET 清单，核对版本、包数、每个包的 `fileName/sizeBytes`；这一步是只读复核，连续 3 次取不到时降级为警告（服务端写入已成功），只有取到且内容不符才判失败。

可选参数：`-DryRun`（只校验不上传）、`-SkipVerify`、`-SkipSyncScriptDeploy`。

### 5.3 服务端为什么要改 `game-file-sync.sh`

游戏包发布走 `Publish-GameDownloadRelease.ps1` → `game-file-sync.sh finalize`，**finalize 会重写 `latest.json`**。旧脚本写死了字段，会把碎片清单加的 `fragmentsUrl` 冲掉。

现在 finalize 写 latest.json 前会检查 `$BASE/fragments/$VER.json`：

- 存在 → 带上 `fragmentsUrl`；
- 不存在 → 不写这个字段。

所以碎片发布和游戏包发布互不覆盖。碎片发布脚本默认会自动更新服务器上的这个脚本（仓库版本 hash 不同就传）。

## 8. 排错

| 现象 | 原因 / 处理 |
|---|---|
| 启动器说 `CrossingVoid.obb.json` 内容对不上 | 旁车字节不对。0.6.0 应为 8,796 B / sha256 `22cc73d4…`；检查 AxTools 是否是本次改后的版本，不要手工格式化/重排这份 JSON |
| 启动器说 `CrossingVoid.version.json` 对不上 | 平台/渠道写错。安卓必须是 `platform=Android`，stable 是 76 B / `858486bd…` |
| 安卓基础碎片 003 只有 338 MiB | 正常，next-fit 在这批 OBB 条目上的实际结果；不是少文件。总 155 条对上即可 |
| 点生成没反应 | 获取版本标记阶段挂全局进度条；按钮会禁用，等它结束 |
| `无法检索变量 '$xxx?t'` / 中文被吃进变量名 | PowerShell 字符串里变量后紧跟中文或 `?`，必须写 `${var}` |
| 导入器说「缺 CrossingVoid.version.json」 | 生成时没补上；检查源目录是否可写，或手动从 dl 下载该版本标记放到打包根 |
| `fragments.json` 缺失但包在 | 直接点「发布碎片清单」，脚本会按现有 zip 重建；PC/安卓命名和安装包都已兼容 |
| 发布成功但 `latest.json` 没 `fragmentsUrl` | 检查服务端 `/srv/scripts/game-file-sync.sh` 是否已更新（脚本默认会传，可用 `-SkipSyncScriptDeploy` 跳过） |
| 安卓发布卡在 90%「正在更新 latest.json」 | 服务器 SSH 被扫描/连接被拖住时，旧的 `ssh`/`sftp` 可能无限等待；脚本已加 `BatchMode`、连接/握手超时和 3 次重试，重试一次即可，不会再无限挂起 |
| 公网校验报 SSL 连接失败 | 本地 PowerShell 7 的 TLS 偶发问题；脚本已重试 3 次，仍失败会降级为警告、任务仍算成功。先看服务端 `latest.json` 是否已写入，公网再用浏览器/curl 复核 |
| 安卓发布到了 PC 段 | 检查前端是否传了 `-ProductSegment crossingvoid-android` |
| 生成后旧文件还在 | 切片模式会清空输出目录；如果没清，检查输出目录是否被 `Validate` 拒绝（盘根/源目录/用户目录/链接） |
| PC 线上清单还是旧名 `零境V0.6基础碎片…` | 需要重新生成 PC 碎片并重发 `crossingvoid/fragments/0.6.0.json`；新名是 `零境V0.6PC基础碎片…`，zip 内部条目名没变 |
